# 여행기록 앱 기본 개발 규칙

## 변경 이력

| 버전 | 날짜 | 작성(수정)자 | 변경 내용 |
|---|---|---|---|
| v1.0 | 2026-09-23 | tokec | 기본 개발 규칙 작성 |
| v1.1 | 2026-09-25 | tokec | Android 카카오지도 네이티브 경로와 로컬 우선 구현 기준 반영 |

## 1. 목표

- Android와 iOS에서 동일한 핵심 기능과 일관된 사용자 경험을 제공한다.
- 여행 기록과 관련 자료를 안전하게 저장하고, 빠르게 검색·조회할 수 있게 한다.
- 필요한 기능만 구현하고 사용하지 않는 추상화와 의존성은 추가하지 않는다.

## 2. 기술 기준

- Flutter와 Dart를 기본 개발 스택으로 사용한다.
- 플랫폼별 코드는 Flutter로 해결할 수 없을 때만 추가한다.
- 외부 패키지는 유지보수 상태, 라이선스, Android/iOS 지원 여부를 확인한 뒤 추가한다.
- 버전과 의존성 변경 후 `flutter pub get`, 정적 분석, 테스트를 실행한다.

## 3. 구조와 코드

- 화면, 상태 관리, 데이터 모델, 저장소 로직을 분리한다.
- 화면 위젯에 파일 저장·네트워크·데이터베이스 로직을 직접 넣지 않는다.
- 파일과 클래스 이름은 역할이 드러나게 작성한다.
- 작은 기능은 기존 코드와 Flutter 기본 기능을 먼저 재사용한다.
- 중복 코드는 공통화하되, 한 번만 사용되는 코드는 억지로 추상화하지 않는다.
- `dynamic` 사용을 피하고 명시적인 타입을 사용한다.
- 사용자에게 표시할 문자열, 날짜, 단위는 중앙에서 관리하고 현지화를 고려한다.

## 4. 플랫폼 대응

- 화면 크기, 안전 영역, 글꼴 크기, 다크 모드를 고려한다.
- Android 뒤로 가기와 iOS 제스처가 자연스럽게 동작해야 한다.
- 권한은 필요한 시점에 최소 범위로 요청하고 거부·제한 상태를 처리한다.
- 사진, 파일, 위치 등 플랫폼 기능은 권한 없이 사용할 수 있다고 가정하지 않는다.
- Android와 iOS에서 동일한 기능을 실제 기기 또는 에뮬레이터로 확인한다.
- 현재 플랫폼 차이: Android 카카오지도 네이티브 경로는 구현되어 있으며 iOS 경로 렌더링은 별도 검증 전까지 완료로 표시하지 않는다.

## 5. 여행 자료와 데이터

- 기록, 사진, 파일, 위치 정보에는 생성·수정 시각을 저장한다.
- 저장 실패, 네트워크 단절, 잘못된 파일 형식, 용량 초과를 사용자에게 이해하기 쉽게 알린다.
- 삭제 기능은 실수 방지를 위해 확인 절차를 제공하고, 복구가 필요한 자료는 즉시 영구 삭제하지 않는다.
- 개인정보와 위치 정보는 필요한 범위만 수집하고 로그에 원문을 남기지 않는다.
- 데이터 형식 변경 시 기존 사용자의 데이터를 읽을 수 있는 마이그레이션 경로를 제공한다.

## 6. UI와 UX

- 로딩, 성공, 빈 상태, 오류 상태를 모두 정의한다.
- 저장·삭제·동기화 결과를 사용자에게 즉시 표시한다.
- 긴 작업은 진행 상태를 보여주고 중복 실행을 막는다.
- 터치 영역은 충분한 크기로 유지하고 색상만으로 상태를 구분하지 않는다.
- 여행 기록 작성 흐름은 최소 단계로 유지한다.

## 7. 품질 규칙

- 커밋 전 `flutter analyze`를 통과시킨다.
- 주요 사용자 흐름은 위젯 테스트 또는 통합 테스트로 검증한다.
- 데이터 저장, 날짜·시간, 권한, 첨부파일 처리는 경계값을 테스트한다.
- 테스트가 실패하면 원인을 해결한 뒤 커밋한다.
- 기능 변경 시 관련 문서와 예시를 함께 갱신한다.

## 8. 변경 원칙

- 한 변경은 하나의 목적만 갖는다.
- 기존 동작을 깨뜨릴 가능성이 있으면 변경 이유와 영향 범위를 기록한다.
- 새 기능보다 기존 기능의 안정성과 데이터 보존을 우선한다.
- 사용하지 않는 코드와 의존성은 제거한다.
