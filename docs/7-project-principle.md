## 1. 문서 목적

`docs/1~6`의 요구사항과 기술 제약을 기준으로 프런트엔드와 향후 백엔드의 구조를 설계하는 공통 원칙을 정의한다. 기술 구조 표현은 `docs/8-tech_diagram.txt`의 다이어그램을 따른다.

현재 프로젝트는 Flutter 앱만 구현되어 있다. 백엔드 디렉토리는 서버 기능이 확정될 때 이 원칙에 따라 추가한다.

현재 Android 구현은 Kakao 지도, `photo_manager` 사진첩 접근, `geocoding` 도시 좌표 조회를 사용한다. 사진 원본은 운영체제 사진첩에 두고 여행별 선택·숨김 메타데이터만 로컬 여행 데이터에 저장한다.

## 2. 모든 스택에 공통인 최상위 원칙

### 2.1 요구사항 우선

- 사용자가 요청한 기능에 직접 필요한 코드만 추가한다.
- 실제 사용처가 하나뿐인 추상화, 설정, 확장 지점을 만들지 않는다.
- 기존 구현과 문서를 먼저 확인하고 같은 역할의 코드와 패턴을 재사용한다.
- 변경 범위를 작게 유지하고, 관련 없는 리팩터링을 함께 수행하지 않는다.

### 2.2 데이터 보존 우선

- 사진, 동영상, 메모, 위치, 결제 자료는 원본과 처리 상태를 구분한다.
- 저장·동기화·공유 실패가 원본 자료 손실로 이어지지 않게 한다.
- 삭제는 사용자 확인 후 수행하고 복구 정책이 필요한 자료는 즉시 영구 삭제하지 않는다.

### 2.3 플랫폼 공통 우선

- 공통 UI와 비즈니스 로직은 Flutter와 Dart로 구현한다.
- Android와 iOS 차이는 플랫폼 경계 안에 격리한다.
- 플랫폼별 권한과 백그라운드 제약을 공통 기능이 정상이라고 가정하지 않는다.

### 2.4 개인정보 최소화

- 위치, 미디어, 결제, 메시지는 목적에 필요한 범위만 수집한다.
- 비밀번호, 토큰, 원본 메시지, 개인정보가 포함된 경로를 로그에 남기지 않는다.
- 외부 공유 전 데이터 범위와 개인정보 포함 여부를 사용자에게 확인받는다.

### 2.5 문서와 구현의 일치

- 기능·화면·데이터 형식·설치 방법이 바뀌면 관련 문서를 함께 검토한다.
- 각 문서의 변경 이력은 기존 행을 삭제하지 않고 새 행으로 추가한다.
- 확인하지 않은 플랫폼 동작이나 외부 서비스 정책은 확정된 사실처럼 기록하지 않는다.

## 3. 의존성과 레이어 원칙

### 3.1 의존성 추가

의존성 선택 순서는 다음과 같다.

1. Flutter·Dart 기본 API
2. Android·iOS 플랫폼 기본 기능
3. 이미 설치된 의존성
4. 유지보수 상태와 양 플랫폼 지원이 확인된 새 패키지

새 패키지를 추가할 때는 사용 목적, Android·iOS 지원 여부, 권한, 라이선스, 대체 가능한 기본 API를 확인한다.

### 3.2 레이어 방향

의존성 방향은 아래처럼 단방향으로 유지한다.

```text
화면(UI) → 기능 로직(상태·유스케이스) → 데이터 접근(저장소·외부 API)
                                      ↓
                               플랫폼 연동 경계
```

- UI는 저장소, 네트워크, 플랫폼 API를 직접 호출하지 않는다.
- 기능 로직은 Flutter 위젯에 의존하지 않는다.
- 데이터 접근은 로컬 저장과 외부 서비스의 차이를 호출자에게 숨긴다.
- 플랫폼 전용 구현은 Flutter가 정의한 최소 인터페이스를 통해서만 사용한다.
- 레이어는 파일 수를 늘리기 위한 형식이 아니라 책임이 실제로 분리될 때만 만든다.

### 3.3 도메인 기준

- `여행 식별자`를 자료를 묶는 기본 기준으로 사용한다.
- 활동 기록은 시각, 장소, 종류, 출처, 처리 상태를 공통으로 가진다.
- 현지 시각과 시간대를 저장해 날짜별 조회가 달라지지 않게 한다.
- 제품 기준은 국내 카카오지도, 국외 Google Map이며, 현재 Android 구현은 카카오지도만 연결되어 있다.
- 로컬 인증은 앱 잠금 해제, Firebase Authentication은 원격 사용자 식별에 사용한다.

## 4. 코드와 네이밍 원칙

### 4.1 공통

- 이름만 보고 역할과 소유 범위를 알 수 있게 한다.
- `dynamic`을 피하고 명시적인 타입을 사용한다.
- 함수는 하나의 책임을 갖고, 부작용이 있으면 이름에 동작을 드러낸다.
- 동일한 용어는 문서·코드·UI에서 일관되게 사용한다.
- 주석은 코드만으로 설명하기 어려운 이유나 제약을 기록한다.

### 4.2 Flutter·Dart

- 파일명은 `lower_snake_case.dart`를 사용한다.
- 클래스와 enum은 `UpperCamelCase`, 변수와 함수는 `lowerCamelCase`를 사용한다.
- 화면 위젯은 `...Page` 또는 `...Screen`, 재사용 UI는 `...Widget`으로 명명한다.
- 기능별 디렉토리와 파일을 우선하고, 한 번만 사용되는 공통 위젯은 만들지 않는다.
- 문자열, 날짜, 단위는 표시 위치에 흩어지지 않게 관리한다.

### 4.3 Kotlin·Swift

- Android는 Kotlin·Gradle의 표준 명명 규칙을 따른다.
- iOS는 Swift·Xcode의 표준 명명 규칙을 따른다.
- 네이티브 코드는 플랫폼 기능을 담당하는 역할을 이름에 드러낸다.
- 플랫폼 채널 메서드와 데이터 키는 Dart·Kotlin·Swift에서 동일하게 유지한다.

### 4.4 백엔드

- API 리소스와 도메인 개념은 `여행`, `이동경로`, `활동 기록`, `사용자`처럼 문서 용어를 따른다.
- 요청·응답 DTO와 내부 도메인 모델을 필요할 때만 구분한다.
- 인증 사용자 `uid`와 자료 소유권을 모든 보호된 데이터에서 검증한다.
- 날짜·시간·좌표·통화 형식은 API 계약에 명시한다.

## 5. 테스트와 품질 원칙

### 5.1 기본 검증

- Dart 코드 변경 후 `flutter analyze`를 실행한다.
- 동작 변경 후 가장 관련 있는 최소 테스트를 실행한다.
- 주요 사용자 흐름은 위젯 테스트 또는 통합 테스트로 검증한다.
- Android와 iOS에서 인증, 권한, 키보드, 뒤로 가기, 공유를 실기기로 확인한다.

### 5.2 우선 테스트 대상

- 현지 날짜와 시간대 변환
- 여행·활동 기록의 연결
- 위치 수집 간격과 빈 위치 처리
- 메모 제목 기본값, 첨부, 저장·수정
- 권한 거부와 네트워크 단절
- 공유 수신 동의와 전송 실패
- 삭제 확인과 자료 보존

### 5.3 백엔드 품질

백엔드가 추가되면 인증·공유 흐름을 포함해 1,000명 동시 접속 목표를 부하 테스트로 검증한다. 측정하지 않은 처리량을 보장 수치로 문서화하지 않는다.

## 6. 설정·보안·운영 원칙

### 6.1 설정

- 환경별 설정은 코드와 분리한다.
- API 키, 토큰, 비밀번호를 저장소에 커밋하지 않는다.
- Android 권한은 `AndroidManifest.xml`, iOS 권한 설명은 `Info.plist`에 실제 기능에 필요한 범위만 선언한다.
- 백그라운드 위치 수집 간격과 배터리 한도는 사용자가 확인·변경할 수 있게 한다.

### 6.2 보안

- 로컬 잠금과 원격 계정 인증을 혼동하지 않는다.
- 로컬 인증 정보와 외부 연동 정보는 운영체제 보안 저장소 사용을 우선한다.
- 서버 데이터는 Firebase `uid`와 권한으로 접근을 제한한다.
- 공유는 수신 동의 후 시작하고 공유 범위를 사용자에게 표시한다.
- 디버그 로그는 디버그 모드에서만 활성화하고 민감 정보를 제거한다.

### 6.3 운영

- 로딩, 성공, 빈 상태, 오류, 권한 거부 상태를 사용자에게 표시한다.
- 긴 작업은 진행 상태와 중복 실행 방지를 제공한다.
- 네트워크 실패는 재시도 가능한 상태로 남긴다.
- 데이터 형식 변경 시 기존 자료를 읽을 수 있는 마이그레이션 경로를 마련한다.
- 외부 서비스 장애가 로컬 자료 조회를 막지 않게 한다.

## 7. 프런트엔드 디렉토리 구조

현재 앱은 `main.dart` 단일 진입점과 `models`, `data`, `services`, `config`를 사용한다. 아래 기능별 구조는 독립 메모·공유·원격 동기화가 실제로 추가되어 파일 규모가 커질 때만 적용한다.

```text
lib/
├── main.dart
├── app/
│   ├── app.dart
│   ├── routes.dart
│   └── theme.dart
├── core/
│   ├── error/
│   ├── logging/
│   ├── permissions/
│   └── platform/
├── features/
│   ├── auth/
│   ├── trips/
│   ├── routes/
│   ├── activities/
│   ├── notes/
│   ├── sharing/
│   └── settings/
└── data/
    ├── local/
    ├── remote/
    └── repositories/
```

### 7.1 프런트엔드 구조 규칙

- 기능 폴더 안에 화면과 해당 기능의 상태·모델·동작을 둔다.
- 여러 기능에서 실제로 공유될 때만 `core/`로 이동한다.
- 지도·위치·미디어·인증 연동은 기능 또는 `core/platform/` 경계 안에 둔다.
- 현재 `main.dart`에는 앱 시작과 화면·기능 구현이 함께 있으므로, 기능 분리는 파일 규모가 커질 때 단계적으로 진행한다.
- 백엔드 URL, API 키, 사용자 자료를 위젯에 직접 하드코딩하지 않는다.

## 8. 백엔드 디렉토리 구조

현재 백엔드는 `src/domain.js`의 검증 로직과 `src/server.js`의 최소 REST API로 구성된다. Node.js와 Firebase Admin SDK를 사용해 Firebase Authentication 토큰을 검증하고 Firestore에 사용자별 자료를 저장한다. 실제 외부 공유 전송은 별도 어댑터로 추가한다.

```text
backend/
├── src/
│   ├── domain.js
│   └── server.js
├── tests/
│   └── domain.test.js
└── README.md
```

### 8.1 백엔드 구조 규칙

- `auth/`는 Firebase 토큰 검증과 사용자 `uid` 추출을 담당한다.
- `trips/`는 여행과 이동경로의 소유권·기간을 검증한다.
- `activities/`는 자료 종류별 저장·조회 계약을 담당한다.
- `sharing/`은 외부 공유와 주변 기기 공유의 권한·동의·전송 상태를 담당한다.
- `common/`에는 실제로 두 모듈 이상에서 사용하는 코드만 둔다.
- 저장소, 외부 API, 도메인 로직을 한 파일에 섞지 않는다.
- 비밀값과 사용자 원본 자료를 테스트 코드나 로그에 넣지 않는다.

## 9. 변경 시 점검 순서

1. 변경이 요구사항과 어느 문서에 연결되는지 확인한다.
2. 기존 호출자와 데이터 흐름을 확인한다.
3. 가장 작은 레이어와 파일 범위를 선택한다.
4. 권한·개인정보·오프라인 실패 영향을 확인한다.
5. `flutter analyze`와 관련 테스트를 실행한다.
6. Android와 iOS 차이를 확인한다.
7. 관련 문서의 변경 이력을 새 행으로 추가한다.
