# 기본 문서 작성 규칙

## 변경 이력

- 문서의 변경이력은 각 문서의 앞부분에 작성한다.
- 작성자/수정자는 tokec으로 기록한다.
- 기존 변경 이력은 삭제하거나 수정하지 않고, 변경할 때마다 새 행으로 추가한다.
- `README.md`도 문서 업데이트 대상에 포함한다.
- 문서 변경 이력은 다음과 같이 작성한다.

| 버전 | 날짜 | 작성(수정)자 | 변경 내용 |
|---|---|---|---|
| v1.0 | 2026-09-24 | tokec | 기본 문서 작성 규칙 작성 |
| v1.1 | 2026-09-23 | tokec | 변경 이력 누적 규칙 추가 |
| v1.2 | 2026-09-23 | tokec | README.md를 문서 업데이트 대상에 포함 |
| v1.3 | 2026-09-23 | tokec | README.md를 프로젝트 루트 문서 예외로 명시 |
| v1.4 | 2026-09-23 | tokec | Mermaid 다이어그램 문서 형식 예외 추가 |

## 1. 문서 목적

- 문서만 읽어도 대상 기능과 사용 방법을 이해할 수 있게 작성한다.
- 실제 구현과 문서 내용이 다르지 않도록 변경 시 함께 갱신한다.
- 같은 내용을 여러 문서에 중복해서 작성하지 않고 기준 문서를 하나로 둔다.

## 2. 파일과 이름

- 문서는 `docs` 폴더에 저장한다.
- 프로젝트 안내 문서인 `README.md`는 프로젝트 루트에 저장한다.
- 파일 이름은 번호와 내용을 조합한다. 예: `1-develop-rule.md`
- 파일 이름은 소문자 영어와 하이픈을 사용한다.
- 문서 형식은 Markdown을 기본으로 사용한다.
- Mermaid 다이어그램은 요청된 대상 파일명이 있으면 `.txt` 형식을 사용할 수 있다.
- 하나의 문서에는 하나의 주제만 담는다.

## 3. 문서 구조

- 문서 첫 줄은 문서 제목(`#`)으로 시작한다.
- 큰 주제는 2단계 제목(`##`), 세부 주제는 3단계 제목(`###`)으로 구분한다.
- 제목 단계는 건너뛰지 않는다.
- 독자가 알아야 할 결론과 사용 방법을 문서 앞부분에 둔다.
- 긴 설명은 짧은 문단과 목록으로 나눈다.
- 절차는 실행 순서대로 번호 목록으로 작성한다.
- 선택지나 조건은 표 또는 목록으로 정리한다.

## 4. 문장과 표현

- 기본 언어는 한글로 작성한다.
- 고유명사와 기술명은 원래 표기를 유지한다. 예: `Flutter`, `Dart`, `Android`, `iOS`
- 명령어, 파일 경로, 코드, 설정 키는 백틱으로 감싼다.
- 한 문장에는 하나의 핵심 내용만 담는다.
- 주어와 동작을 분명히 작성하고 불필요한 수식어를 줄인다.
- 같은 용어는 문서 전체에서 같은 표현으로 사용한다.
- 추측은 사실처럼 작성하지 않고, 확인이 필요한 내용은 별도로 표시한다.
- 독자에게 필요한 정보만 작성하고 배경 설명은 필요한 만큼만 덧붙인다.

## 5. 코드와 예시

- 코드 예시는 실제로 실행 가능한 최소 예시를 사용한다.
- 코드 블록에는 언어를 지정한다. 예: ` ```dart `
- 코드 설명은 코드 앞이나 뒤에 짧게 작성한다.
- 운영 환경의 비밀번호, 토큰, 개인정보를 예시에 포함하지 않는다.
- 경로와 명령어는 복사해 실행할 수 있는 형태로 작성한다.
- 예시가 특정 플랫폼에만 적용되면 대상 플랫폼을 명시한다.

## 6. 링크와 참고 자료

- 링크 문구만 보고도 연결된 자료의 내용을 알 수 있게 작성한다.
- 깨진 링크를 남기지 않는다.
- 외부 자료를 참고하면 출처와 확인 날짜를 기록한다.
- 외부 자료의 내용을 그대로 복사하지 않고 프로젝트에 필요한 내용으로 요약한다.

## 7. 변경과 검토

- 기능, 화면, 데이터 형식, 설치 방법이 바뀌면 관련 문서를 함께 검토한다.
- 더 이상 맞지 않는 내용은 즉시 수정하거나 삭제한다.
- 문서를 추가하거나 크게 수정할 때는 제목, 예시, 링크, 명령어를 확인한다.
- 문서에 적은 명령어와 경로가 현재 프로젝트에서 유효한지 확인한다.
- 검토가 끝난 문서는 맞춤법, 제목 단계, 목록 형식, 코드 표시를 확인한다.

## 8. 문서 작성 완료 기준

- 문서의 목적과 대상 독자가 분명하다.
- 필요한 절차를 처음부터 끝까지 따라 할 수 있다.
- 예시와 명령어가 현재 구현과 일치한다.
- 깨진 링크와 민감한 정보가 없다.
- 다른 문서와 용어와 규칙이 충돌하지 않는다.
